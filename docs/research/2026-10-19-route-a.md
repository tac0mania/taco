# Research: Route A, distilgpt2 fine-tuned on logs (2026-10-19)

This note records Route A (HANDOFF §4, ADR 0012). The question: does distilgpt2 (82M
parameters, 6 blocks, GPT-2 architecture), fine-tuned on logs and converted to integers, make
logs smaller than GPT-2 small? The most important case is a log system that the model did not
see in training. All numbers are measured on 2026-10-18 and 2026-10-19, unless a number has a
different label. "bpb" is bits per byte.

## 1. Results in short

- **Seen log systems: the fine-tuned model is much better.** On the tails of the 12 training
  systems (bytes that training did not use), the fine-tuned model gives 0.281 bpb. GPT-2 small
  gives 0.848 bpb, and xz -9e gives 0.800 bpb on the same bytes. The model alone is 67 %
  smaller than GPT-2 alone.
- **Unseen log systems: the fine-tuned model ties GPT-2.** On the 4 held-out systems (Apache,
  HealthApp, Proxifier, Zookeeper), the fine-tuned model gives 0.684 bpb and GPT-2 gives 0.689
  bpb (0.7 % smaller). The result changes by system: Apache −21 %, HealthApp −10 %, Proxifier
  +42 %, Zookeeper +6 %. Plain distilgpt2 gives 0.825 bpb, so the fine-tune gains 17 %.
- **With the match model and the mixer (the `logs` profile), GPT-2 wins on unseen systems.**
  On 16 KiB of each held-out system, `taco fold --profile logs` gives 3,879 bytes with the
  fine-tuned model and 3,709 bytes with GPT-2 (+4.6 %). On 16 KiB tails of 4 training systems,
  it gives 3,593 bytes against 7,672 bytes (−53 %). xz -9e gives 4,664 and 10,872 bytes.
- **English-heavy log lines of unseen systems:** the fine-tuned model is 4 % worse than GPT-2
  (0.638 against 0.612 bpb). The `text` profile must keep GPT-2.
- **The integer model loses more on the fine-tuned model.** Integer against float (ideal size):
  +6.6 % on all 373 windows, +16.7 % on the tails, −2.3 % on the held-out systems. For plain
  distilgpt2 the loss is −0.2 %. A probe of the activation ranges on the val split reduces the
  loss there from +19.7 % to +9.9 %. On the evaluation windows, the probe makes the tails 8 %
  smaller and the held-out systems 3 % larger (section 6).
- **Speed.** distilgpt2 is 1.5 to 1.7 times faster than GPT-2: CUDA full window at batch 224,
  14,610 against 8,601 tokens/s; CUDA prefill 8 x 1,024, 43,563 against 27,624 tokens/s; CPU one
  thread, about 60 against 42 tokens/s (loaded machine).
- **Bit-exact.** CUDA gives the same weights as the CPU on 6 windows (2,386 steps) and the same
  2,386 coder intervals. Two conversions give the same model file. Two folds give the same
  container. The Mac (ARM) restored containers that devbox (x86) made, byte for byte.
- **Recommendation (section 9):** keep `gpt2.hsm` as the model of the `logs` profile now. Do
  not ship the fine-tuned model as the general log model. Its value is for log systems that
  are in its training data. Continue Route A with three changes: a range rule for confident
  models, more log systems in training, and a gate that includes the match model and the mixer.

Use `heldout` and `tail` for decisions.

warm-up steps and a cosine decay to 10 %. A step has 32 sequences of 1,024 tokens. The run

ran at the same time). The GPU ran at a power limit (the SM clock changed during the runs).
The decode numbers at batch 1, 32 and 128 changed much between runs, so this note does not use
them. The ratio agrees with the parameter count: 6 blocks and the same 38.6M-parameter logit
matrix, against 12 blocks (est. 1.5 for the matrix products).

Bit-exact checks (measured):

- `hardshell-cuda` example `gpt2 equiv` with `distil_logs.hsm`: the CPU, the CUDA decode, the
  op-level decode and the prefill gave the same SHA-256 of all weights on 6 windows (2,386
  steps: the 4 held-out 2k files, alice29.txt and a long window of 1,100 steps). The CUDA coder
  op gave the same 2,386 intervals as the CPU `FreqTable`.
- Two folds of Apache (16 KiB) with `distil_logs.hsm` gave the same container (SHA-256
  `ce8f67a0…`).
- devbox (x86) restored Apache and Zookeeper (16 KiB) byte for byte with both models.
- Cross-machine: the Mac (ARM) restored two containers that devbox (x86) made with
  `distil_logs.hsm`, byte for byte (Zookeeper 16 KiB, 943 bytes; Android tail 16 KiB, 624
  bytes; the checksum verified). The Mac CLI was built from the working tree at 23:59 +04.

## 9. Recommendation

1. **Keep `gpt2.hsm` as the model of the `logs` profile (ADR 0012).** On log systems that the
   model did not see, the fine-tuned model alone ties GPT-2. With the match model and the
   mixer it is 4.6 % larger. Users compress their own logs, which are not in Loghub. Thus the
   held-out result is the result that a user gets.
2. **Do not replace GPT-2 in the `text` profile.** The fine-tuned model is 4 % worse on the
   English-heavy lines of unseen systems.
3. **A fine-tune helps on the log systems that it saw: 53 % smaller than GPT-2 with the match
   model, and 67 % smaller alone.** This supports a later product option: a model that is
   fine-tuned on the logs of one customer. That option needs a decision from Rohit, because the
   decoder must have the same model file (CLAUDE.md §1 rule 3).
4. **If Route A continues, do these steps in this order:**
   1. Fix the range rule for confident models. Select the `ln_f` and GELU ranges on the val
      split (section 6: +19.7 % to +9.9 %), and check them on held-out systems too (the
      probe made the tails 8 % smaller and the held-out systems 3 % larger). This needs an
      ADR change (ADR 0004 section 7) and a new recipe. The `gpt2.hsm` file must not change.
   2. Train on more log systems (other public logs, not only Loghub) and keep more systems
      out of training. Measure the held-out result again.
   3. Use a gate that includes the match model and the mixer: the fine-tuned model must make
      the held-out systems at least 5 % smaller than GPT-2 with the same `logs` profile.
      (The 5 % is a proposal, not a measurement.)
5. **Speed is not a reason alone.** distilgpt2 is 1.5 to 1.7 times faster. The speed work
   (CUDA, SIMD, the skip rule) gives more for GPT-2.

## 10. Commands

Do not commit weights or data. The artifacts are in `~/taco-train` on devbox, outside the
mirror (`scripts/dx` deletes files in the mirror that the Mac does not have).

```bash
# Data (run from tools/, on devbox; the archives are in ~/taco-train/dl)
nice uv run python -m finetune.prepare --archives ~/taco-train/dl --work ~/taco-train/work
nice uv run python -m finetune.pack --work ~/taco-train/work --out ~/taco-train/work/train_data.npz
nice uv run python -m finetune.evalset --work ~/taco-train/work

# Training (devbox, tmux; resumes from run3/ckpt/latest after a failure)
uv venv -p 3.12 ~/taco-train/venv   # then install torch 2.11.0+cu128 and transformers (section 3)
~/taco-train/venv/bin/python tools/finetune/train.py --data work/train_data.npz --out run3 \
    --model models/distilgpt2 --steps 2446 --micro 2 --accum 16 --lr 2e-4 --warmup 150 \
    --eval-every 200 --save-every 400 --val-blocks 24 --seed 20261018

# Conversion (run from tools/)
nice uv run python -m convert.calibrate --model M/model.safetensors --windows work/calib_windows.txt \
    --stats-out out/distil_logs.stats.toml --channels-out out/distil_logs.channels.npz
nice uv run python -m convert.gpt2 --model M/model.safetensors --stats out/distil_logs.stats.toml \
    --out out/distil_logs.hsm --new-hash
# NOTE: since ADR 0014 the converter checks its output against tools/convert/expected.toml.
# The first conversion of a new model needs --new-hash; add the printed entry to that file.

# Measurement
eval_bits out/distil_logs.hsm work/eval/windows.txt --threads 6 --chunk 32 --digest > eval.tsv
nice uv run python -m finetune.floateval --model M/model.safetensors --windows work/eval/windows.txt --out f.json
uv run python -m finetune.report --eval work/eval gpt2=eval_gpt2.tsv distil=eval_distil_plain.tsv \
    distil-logs=eval_distil_logs.tsv --float distil-logs=f.json
```
