# Research: logs, the match model and the mixer (2026-10-18)

This note records the measurement behind ADR 0010. The question: can Taco make logs much
smaller than xz and zstd? All numbers are measured on 2026-10-18, unless a number has a
different label. "bpb" is bits per byte.

## 1. Results in short

- **On logs, the match model and the mixer make Taco 35 % to 50 % smaller than GPT-2 alone**
  (16 Loghub files, measured, exact table cost). GPT-2 alone gives 1.006 bpb with 16 KiB
  blocks. GPT-2 with the match part gives 0.658 bpb.
- **Against xz and zstd, the margin depends on the block size.** With 16 KiB blocks (the Taco
  default) the 16 Loghub files are 32 % smaller than with xz -9e and 31 % smaller than with
  zstd -19 --long=27. With 1 MiB blocks (the whole file) they are 10.1 % smaller than xz -9e
  and 16.7 % smaller than zstd -19 --long=27. Large blocks help xz and zstd more than they help
  Taco.
- **By file (1 MiB blocks):** Taco is the smallest on 16 of 18 logs. The margin against the best
  general compressor is 0.9 % (Spark) to 29.9 % (Apache error log). Taco loses on two files:
  OpenStack (random hex ids; xz is 11.8 % smaller) and the nginx JSON lines (bzip2 is 7.9 %
  smaller; Taco is 1.9 % smaller than xz).
- **Web access logs (Apache, 1 MiB):** 0.400 bpb, 11.6 % smaller than xz and 17.0 % smaller than
  zstd --long. With 16 KiB blocks, 43 % smaller than both.
- **Text does not become worse. It becomes better.** On the 14 phase 0 text files, the part
  makes every file smaller: −2.1 % (man page) to −38.4 % (C source), −9.9 % in total, with 16
  KiB blocks. The largest gains are on files with tab or CR characters, which GPT-2 predicts
  badly (est. cause).
- **Where the bits go:** 78 % to 90 % of the remaining bits are in the 4 % to 41 % of tokens
  that the match model predicts wrongly, and 38 % to 88 % are in digit tokens. Numbers that
  occurred before in the block cost 12 % to 86 % of the bits. New numbers (random ids,
  timestamps) cost 1.8 to 4.6 bits for each digit; a uniform random digit costs 3.32 bits.
- **The Rust crate gives the same bits as the simulation.** `crates/taco-match` (19 tests) and
  the Python copy give the same golden hashes. The CUDA HardShell gives the same GPT-2 facts as
  the NumPy simulation on 86,345 tokens (0 differences).
- **Recommendation:** use the match part in the `logs` profile, and also test it in the `text`
  profile. The gain against xz with large blocks (10 %) is not a wide margin yet. A model for
  numbers and fields is the next step (section 9).

## 3. Method

1. **Tokens.** The tool tokenizes each file in blocks of 16 KiB with the Python BPE of
   `tools/baseline` (ADR 0007 section 2: a token never crosses a block boundary). A block of
   64 KiB, 256 KiB or 1 MiB is a sequence of 16 KiB token blocks.
2. **GPT-2.** `logs.gpt2pass` runs the integer GPT-2 on each window. The context starts again
   at each 16 KiB block start and after 1,024 tokens (plan §7.7), as Taco does today.
   `logs.fastsim` is `convert.intsim` with float32 products where float32 is exact (all partial
   sums are integers below 2^24). Its weights are equal to the weights of `convert.intsim`, bit
   for bit, on two windows (measured). `convert.intsim` agrees with HardShell to 1e-6 bits on a
   full window (integer-GPT-2 research note). For each token the pass keeps the weight sum,
   the weight of the actual token, the exact plan §5.1 frequency of the actual token, the 8
   largest weights, and the weight of every token that the match model can predict.
3. **Match model and mixer.** `logs.matchmodel` and `logs.mixer` are the integer rules of
   ADR 0010 in Python. The match model sees the whole block. The mixer starts again at each
   block start. The weights of the pass are integers, so the mixer state of the simulation is
   exactly the state of the Rust crate.
4. **Exact table cost.** `logs.sim final` computes, for each token, the frequency of the actual
   token in the plan §5.1 table of the mixed weights. The pass does not keep all 50,257
   weights of each row, so two terms have bounds: the shift and 1-floor of the other weights
   (at most 50,256 units of a sum of about 2^56 or more) and the remainder of plan §5.1 step 3
   (0 to 50,256 counts, only for the largest weight). The tables give the upper bound. The
   width of the bounds is less than 0.00002 bpb on every file (measured).
   `logs.validate` runs the full rows again (on the Mac) for the first windows of a file and
   checks that the exact full-row cost is inside the bounds (section 5).
5. **Python and Rust.** The Rust crate and the Python copy give the same SHA-256 for the
   predictions and for all mixed weights of a synthetic log of 4,000 tokens, with the V1 tables
   and with tables of 2^6 entries (measured, `crates/taco-match/tests/golden.rs`,
   `python -m logs.vectors`).
6. **Sizes.** "Taco" sizes are the exact table cost plus an estimate of the container: 88
   bytes, and 9 bytes for each block (the block table, the token count, the coder flush; est.).
   The coder adds 0.021 % to the table cost (phase 0, measured); the tables do not include
   it. The general compressors are the command-line programs on the Mac (Apple gzip 479,
   bzip2 1.0.8, xz 5.8.3, zstd 1.5.7). Each block is compressed alone, and each output is
   decompressed and compared.
7. **Tuning.** The constants of the mixer come from a small grid on two files (HDFS and
   Apache, the first files of the pass). The other 16 log files and the 14 text files are held
   out.

Findings:

- **The misses hold the bits.** The match model is wrong for 4 % to 41 % of the tokens, and these
  tokens hold 78 % to 90 % of the bits. The correct predictions cost little.
- **Numbers hold most of the bits:** 38 % to 88 % of the bits are in digit tokens.
- **Repeated numbers are the largest part that a model can still remove.** They cost 12 % to
  86 % of the bits, at 0.26 to 1.37 bits for each digit. Examples: IP addresses, ports, ids
  and byte counts that occur again in a different line. The match model misses them because
  the context before the number is different (another template, or another field order). On
  `nginx_json.log` they are 86 % of the bits. Possibly this is why bzip2 is smaller there: its
  block sort puts equal values next to each other (UNVERIFIED).
- **New numbers are near their limit.** Random ids and new timestamps cost 1.8 to 4.6 bits for
  each digit. A uniform random digit costs 3.32 bits. HDFS has random block ids of 19 digits
  (66 % of its bits). Thus a better model can make HDFS only a little smaller (est.), and xz is
  only 1.4 % larger than Taco there. Timestamps grow in small steps; a model of the difference to the last value can
  remove a part of their cost (est.).
- **Hex ids.** OpenStack has random request ids in hexadecimal (UUIDs). GPT-2 tokenizes them in
  irregular parts, so new numbers cost 4.5 bits for each digit there. xz is 11.8 % smaller.
- **Speculative decoding has long drafts.** 40 % to 94 % of the log tokens are in hit runs of 4
  or more tokens. The mean run length for a token is 7 to 454 tokens.

  blocks. The falling rate (160 to 16) is near the best for both. The agreement bit gave −0.7 % to −2.0 %
  on HDFS and −4 % to −12 % on Apache.

## 8. Limits

- **Not the real program.** The numbers come from a simulation of the integer rules on the
  facts of one GPT-2 pass. The Rust crate gives the same bits as the Python copy (golden
  vectors), but `crates/taco` does not use the crate yet. A real `taco fold` with the logs
  profile must repeat the measurement.
- **GPT-2 windows.** GPT-2 starts its context again at each 16 KiB step for all block sizes.
  Taco with a block of 1 MiB starts again only after 1,024 tokens. Thus the GPT-2 part of the
  large blocks is a little pessimistic (est.: less than 1 %, from the cost of the first tokens
  of a window).
- **Tokens at the 16 KiB boundaries.** A real block of 64 KiB or more can tokenize a few
  tokens differently at the 16 KiB boundaries (est.: less than 0.1 % of the tokens).
- **Three engines.** `fastsim` on devbox made 7 log files, `fastsim` on the Mac made the 14
  text files, and hardshell-cuda on devbox made 11 log files. `fastsim` is exact for all
  products. The LayerNorm statistics and one attention rescale use float64 sums (as
  `convert.intsim`), so the Mac and devbox can differ in rare last-unit cases (UNVERIFIED for
  the text files). On Linux_2k.log, `fastsim` on devbox and hardshell-cuda gave the same facts
  (section 5).
- **Container estimate.** The container cost (88 bytes and 9 bytes for each block) is an
  estimate. The coder overhead (0.021 %, phase 0) is not in the table cost.
- **Tuning.** The mixer constants come from two files (HDFS, Apache). The other files are held
  out, but the grid was small (section 3, item 7).
- **Speed.** The simulation does not measure the speed of Taco. The part adds about 0.1 ms to
  a token that costs about 18 ms in HardShell (ADR 0010 section 7).

## 9. Recommendation and next steps

1. **Use the match part in the `logs` profile** (ADR 0010, mixer rule version 1). It is
   integer only, costs about 0.1 ms for each token (less than 1 % of a HardShell step), and
   makes logs 35 % to 50 % smaller than GPT-2 alone (measured).
2. **The gain against the best general compressor is large with small blocks and moderate with
   large blocks.** With 1 MiB blocks: −10.1 % against xz and −16.7 % against zstd --long on the
   16 Loghub files, −11.6 % / −17.0 % on the Apache access log, −1.9 % / −12.0 % on JSON
   lines, and +7.9 % against bzip2 on JSON lines. Against xz with large blocks, the margin is
   not wide yet. The gain is more than 10 % against zstd --long with every block size.
3. **Next step: a model for numbers and fields** (est. gain, not measured):
   - A second match model with a sparse context: the hash of the last tokens that are not
     digits (the template position). It predicts the number that followed the same template
     position before. Repeated numbers cost 12 % to 86 % of the bits now.
   - A cache of recent field values (IP addresses, ids) as a third input of the mixer, with a
     context of the field name (JSON key, or the token before the value).
   - A difference model for timestamps (the digits of the last timestamp plus a small step).
   - A rule for hexadecimal ids (OpenStack): code them as digits of a fixed width with a flat
     table, not with GPT-2.

   Each one is a new mixer input, so the mixer of rule version 1 extends to it with one more
   weight for each set. The candidate columns of the pass hold only the predictions of the
   match model. A new model needs the weights of its own predictions, so the pass must run
   again: about 50 minutes for all 32 files on the RTX 3060 with `tools/logs/dump` (est., from
   the measured 1,000 tokens/s).
4. **Test the match part in the `text` profile.** It made all 14 text files smaller (−9.9 % in
   total). If the lead agrees, the `text` profile can use it too (ADR 0012 decision).
5. **Measure the real program.** When `crates/taco` uses `taco-match`, repeat the 1 MiB numbers
   with `taco fold`, with GPT-2 restarts only after 1,024 tokens, and run the cross-machine
   check.
