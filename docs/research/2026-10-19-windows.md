# Research: native Windows x86 build and cross-machine check (2026-10-19)

This note records the first native Windows build of Taco (plan §11.3, product-v1 §1 and item
12). The platforms agent ran it on the Windows side of devbox. `scripts/wcheck` repeats it from
the Mac. All numbers are measured, unless a number has a different label.

## 1. Results in short

- **Windows builds Taco with a small, per-user toolchain.** Rust 1.99.0 with the host
  `x86_64-pc-windows-gnu` and the w64devkit GCC (for `zstd-sys`) use 1.6 GB. Visual Studio
  Build Tools are not necessary.
- **All CPU tests pass, with the golden hashes of the Mac unchanged.** 313 passed, 0 failed,
  1 ignored (`cargo test --workspace --release`, without the two GPU crates), at `a4c8fb8` and
  again at `5682f46`.
- **Windows makes the same `.taco` files as the Mac.** 9 of 9 SHA-256 equal, in the first run
  (`f26bca1`) and in the final run (`5682f46`). The Linux
  `.taco` files of the last xcheck have the same hashes, so the Mac, Linux and Windows agree.
- **Windows restores the files of the Mac byte for byte.** 9 of 9.
- **wgpu finds 6 adapters natively.** The op tests of `hardshell-gpu` pass on Vulkan (NVIDIA
  RTX 3060 and AMD Radeon iGPU). OpenGL passes on one test thread only.
- **DX12 fails with FXC and passes with DXC.** The old shader compiler FXC (shader model 5.1)
  cannot compile 7 of the 14 kernels of `hardshell-gpu`. With DXC (`dxcompiler.dll`, shader
  model 6), all 12 GPU tests (ops, coder and GPT-2) pass on DX12 on both GPUs (§8.2).
- No change to `crates/` was necessary.

All files are in `C:\Users\rohit\taco-win`. The installer had `--no-modify-path`, so no user or
system setting changed. `env.cmd` in that directory sets the environment for one console only.
To remove everything, delete the directory.

Install steps (cmd.exe, in `C:\Users\rohit\taco-win`):

1. Download `rustup-init.exe` from
   `https://static.rust-lang.org/rustup/dist/x86_64-pc-windows-gnu/rustup-init.exe`. Compare
   its SHA-256 with the `.sha256` file next to it.
2. Set `RUSTUP_HOME=%CD%\rustup` and `CARGO_HOME=%CD%\cargo`.
3. Run `rustup-init.exe -y --no-modify-path --profile minimal --default-host
   x86_64-pc-windows-gnu --default-toolchain 1.99.0 -c rustfmt -c clippy`.
4. Download `w64devkit-x64-2.10.0.7z.exe` and compare its SHA-256 with the release digest
   (`18d0a4c7…3b5e`). Run `w64devkit-x64-2.10.0.7z.exe -o%CD% -y`.
5. Make an empty archive: `w64devkit\bin\ar.exe rcs lib-extra\libgcc_eh.a` (see §8.1).
6. `scripts/wcheck` writes `env.cmd` and copies the source.

Why this toolchain:

- The `-gnu` target needs no Visual Studio. The MSVC target needs the Build Tools and the
  Windows SDK (est. 6 to 8 GB).
- `zstd-sys` compiles the zstd C library with the `cc` crate. Thus the build needs a C compiler.
  w64devkit is the smallest portable MinGW-w64 GCC that we found (67 MB download).
- w64devkit uses msvcrt, the same C runtime as the Rust `x86_64-pc-windows-gnu` target. Thus
  one program does not mix two C runtimes. llvm-mingw and the newer WinLibs builds use UCRT.

## 8. Problems

### 8.1 The linker does not find `libgcc_eh`

The first build failed at the link of each build script: `ld.exe: cannot find -lgcc_eh`.
w64devkit builds GCC without shared libraries. Its unwinder (`_Unwind_RaiseException`,
`_GCC_specific_handler`) is in `libgcc.a`, and there is no `libgcc_eh.a`. rustc asks for
`-lgcc_eh`. An empty `libgcc_eh.a` in `lib-extra`, with `LIBRARY_PATH` set to that directory,
satisfies the request. The unwinder then comes from `libgcc.a`. w64devkit itself does not
change.

### 8.2 DX12: FXC cannot compile the shaders, DXC can

**Symptom.** On both GPUs, `Device::create_compute_pipeline` fails for the shader `selftest`:
`FXC D3DCompile error (Unspecified error (0x80004005)): internal error: compilation aborted
unexpectedly`. Each failed test took about 97 s before the error.

**Cause: the shader compiler FXC.** wgpu 30 selects the DX12 shader compiler with
`Dx12Compiler::Auto`: static DXC if wgpu has the feature `static-dxc`, then `dxcompiler.dll` on
the DLL search path, then FXC (`d3dcompiler_47.dll`, version 10.0.19041.3636 on this machine).
`hardshell-gpu` does not enable `static-dxc`, and Windows 10 does not include DXC in the system
directory. Thus the tests used FXC. FXC supports shader model 5.1 only. naga then writes HLSL for
shader model 5.1.

**A test of each kernel with FXC.** To find the parts that FXC refuses, a small program (in the
scratch directory, not in the repository) used naga 30.0.1 to translate each WGSL module of
`hardshell-gpu` (with `int.wgsl` and `common.wgsl`) to HLSL for shader model 5.1. A PowerShell
script then called `D3DCompile` of `d3dcompiler_47.dll` for each entry point (target `cs_5_1`,
flag `D3DCOMPILE_ENABLE_STRICTNESS`, the flags of wgpu). The naga options were the defaults, not
the options of wgpu-hal (binding map). The errors are in the code of the functions, so this
difference does not change them.

| Entry point | FXC result | FXC message |
|---|---|---|
| `add`, `kv_store`, `table`, `logits_max`, `logits_weights` | compiles | — |
| `matvec`, `gemm` | compiles, slowly (77 s and 43 s) | — |
| `embed`, `linear_i32`, `logits_scale` | fails | X3500: array reference cannot be used as an l-value; not natively addressable |
| `attend`, `linear_i8` | fails | X3500, and X3511: forced to unroll loop, but unrolling failed |
| `norm` | fails after 16 s | X3511: unable to unroll loop (60 iterations) |
| `coder_interval` | fails after 17 s | X3511: unable to unroll loop (111 iterations) |
| `selftest` | fails | internal error: compilation aborted unexpectedly |

Thus 7 of the 14 production kernels do not compile with FXC. The ops test found only the first
of them, because `GpuOps` compiles `matvec`, `gemm` and `selftest` only. The 97 s of each failed
test agree with the time of `matvec` and `gemm` (77 s and 43 s here, on a loaded CPU).

The errors come from three constructs of our WGSL:

1. **A write to a vector component with a run-time index.** X3500 points to `u128_pow2` in
   `int.wgsl`: `r[s >> 5u] = 1u << (s & 31u)` on a local `vec4<u32>`. FXC cannot write a
   component of a register at a run-time index. It must unroll the loop around such a write, and
   when it cannot unroll, it gives X3511.
2. **Long loops.** FXC tries to unroll the loops of `norm` (60 iterations) and `coder_interval`
   (111 iterations), and stops.
3. **The large `switch` of `selftest`.** One case alone also fails for the cases of `rescale`,
   `isqrt_u128`, `u128_mul64`, `shift_round` and `u128_div_small` (internal error). The cases of
   `i64_floor_div_small`, `u64_div`, `clamp_wide` and `dot4I8Packed` compile.

The errors are limits of FXC, not errors in the WGSL. naga accepts the modules, and Vulkan,
Metal and DXC compile them.

**DXC fixes it (measured).** The machine has `dxcompiler.dll` 1.9.2607 from Microsoft Edge
(signed by Microsoft Corporation). wgpu 30 needs version 1.8.2502 or later. A copy in
`C:\Users\rohit\taco-win\dxc` (no download), on `PATH`, with `WGPU_DX12_COMPILER=dxc`, made
wgpu use DXC. Then all 12 GPU tests pass on DX12 on the NVIDIA and the AMD GPU (§7). DXC
compiles for shader model 6, where these constructs are native.

**Options for the release.** ADR 0008 names "DX12 or Vulkan" for Windows with AMD or Intel
GPUs. The owner of `crates/hardshell-gpu` must select one of these:

1. Ship `dxcompiler.dll` (from the DirectXShaderCompiler releases of Microsoft; licence
   UNVERIFIED for redistribution) next to `taco.exe`. `Auto` then finds it with no code change.
   The test of this note used this path. The file adds about 20 MB.
2. Enable the wgpu feature `static-dxc`. DXC is then in `taco.exe`. wgpu-hal 30.0.1 adds its
   source, `mach-dxcompiler-rs`, only for the target `x86_64-pc-windows-msvc`
   (`target_env = "msvc"` in its `Cargo.toml`). Thus this option needs the MSVC target and the
   Visual Studio Build Tools (§3). On the `-gnu` target of this note, the feature does nothing.
   The change is in the root `Cargo.toml`, so the lead must approve it.
3. Use Vulkan on Windows. It passes on both GPUs of this machine. Some Windows machines have no
   Vulkan driver.
4. Change the WGSL for FXC: no run-time index on a write to a vector, and loops that FXC need not
   unroll. This changes 7 kernels and each needs the bit-exact tests again. We do not recommend
   it, because FXC is not maintained.

The CPU path does not use wgpu. Thus `taco` on Windows works on every machine, with or without
DXC.

### 8.3 OpenGL: parallel tests on one device panic

With parallel tests, two tests panic in `wgpu-hal-30.0.1/src/gles/device.rs:1622`, at the lock
of the GL context in `create_compute_pipeline`. With `--test-threads=1`, all 4 tests pass. The
tests share one device for the whole process (`tests/support/mod.rs`). A WGL context is current
on one thread only. A `taco` that uses OpenGL must use the device from one thread.

### 8.4 The committed tree moved during the work

The lead committed `2aa86bb` (tools only), `f26bca1` (`hardshell-cuda` only) and `5682f46`
(tools only) during the work. The first test run (§5) was on `a4c8fb8`. The first check (§6) was
on `f26bca1`. The final run of `scripts/wcheck` (tests and check) was on `5682f46`. The crates of
the fold path are the same in all these commits.

### 8.5 A fault of `scripts/wcheck` (fixed)

cmd.exe keeps the space before `&&` in `set TACO_JOBS=3 && ...`. Thus the second cargo command
of the test step received the job count `3 ` and stopped: `could not parse "3 "`. The tests of
the first command had passed. The script now uses the quoted form `set "TACO_JOBS=3"`, before
`env.cmd` reads the value.

## 9. How to repeat

On the Mac, after `scripts/xcheck`:

```
scripts/wcheck          # tests, then the Windows half of the cross-machine check
scripts/wcheck tests    # tests only
scripts/wcheck fold     # the Windows half only
```

To repeat the DX12 test with DXC (§8.2), in cmd.exe after `env.cmd`: put a copy of
`dxcompiler.dll` (1.8.2502 or later) in a directory, add that directory to `PATH`, and set
`WGPU_BACKEND=dx12`, `WGPU_DX12_COMPILER=dxc` and `HARDSHELL_GPU_ADAPTER=NVIDIA` (or `AMD`).
Then run `cargo test --release -p hardshell-gpu`. `C:\Users\rohit\taco-win\dxc.ps1` does this
for the three test binaries.

`scripts/wcheck` copies the committed `HEAD` (never the working tree). It writes its results to
`tools/data/xcheck/win/`. The Windows `.taco` files are equal to the files of the Mac, so an
unfold of them on the Mac gives nothing new, and the script does not do it.
